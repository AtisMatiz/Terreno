## Standing rules (apply to every future session on this project)

- Ask a question once, then wait — no re-asking, no restating answers already given. (Also in CLAUDE.md, both global and project-level.)
- Claude can and should operate GitHub Actions directly (trigger runs, poll status, read logs via the `mcp__github__actions_*` / `get_job_logs` tools) instead of asking the user to download/paste logs.
- Repo `AtisMatiz/Terreno` is **public**, so GitHub Actions minutes are free/unmetered — job timeouts can be raised generously without a real cost tradeoff; the only reason to keep them bounded is as a backstop against a genuine hang.
- **There is no local run anymore.** The user dropped it completely (2026-08-12): no `perfis.local`, no `scripts/run_local.sh`, no double-click Mac app. Everything runs in `perfis.ci` (the only profile now) via GitHub Actions. If a source needs a residential IP or a machine kept on, the answer is a better transport in `terreno/http.py`, not "run it locally" — that door is closed by explicit decision, not by oversight.
- PGFN and `olx` are in `perfis.ci`; both confirmed producing genuine responses via the fixed transports (2026-08-12/13, see Known bugs). `wimoveis` and `imovelweb` are **disabled** (`fontes.wimoveis: false`, `fontes.imovelweb: false`): both refused by ZenRows regardless of mode (quick or `js_render`) — a clean, immediate 404/422, not a timing issue. "Measured clearing in a diagnostic" and "confirmed producing real listings" are different claims — always confirm with a real per-source test run (`testar_fonte.yml`), not just a status code.
- **A source returning zero results is not evidence of a block.** Established the hard way, three separate times: VivaReal's zero was our own oversized `size` param, Mercado Livre's was a missing OAuth token, Facebook's was a payload that matched no field in the actor's schema. Read the response body before concluding anything about the network.
- **Measure in the right place.** This sandbox routes through a TLS-terminating proxy, so any fingerprint measurement taken here is meaningless — but GitHub Actions runners do **not** intercept TLS, they merely have a datacenter IP. Those are different questions and conflating them cost real time. `scripts/diagnostico.py` + the `diagnostico` workflow exist to answer them where the answer means something.
- When polling a long-running GitHub Actions run, use a real external timer (`Monitor` with `curl`, or a `Bash --run_in_background` loop hitting the GitHub API) — never judge run duration from this sandbox's own elapsed time / background-sleep completions, which do not reliably track real wall-clock time here. Misreading elapsed time as "stuck" previously caused a live, healthy run to be cancelled by mistake.
- Front-load every access request for the session's likely work at the start (check `SuggestConnectors`/`ListConnectors` before asking for a raw key) rather than piecemeal mid-task. Not standing authorization for destructive/production-facing/hard-to-reverse actions — those still get a check-in at the moment they're taken, regardless of what's been granted upfront.
- Delegate cheap, judgment-free subtasks (file/codebase search, fetching/summarizing docs, running a known script and reporting results, repetitive checks across files) to Haiku subagents (Agent tool, `model: "haiku"`) instead of doing them inline. Reserve the default model for real judgment calls. **This was violated on 2026-08-12**: five parallel agents were spawned without `model:` set and silently inherited Opus (~370k subagent tokens for work that was substantially mechanical). The `Agent` call's default is the parent's model, not Haiku — the model kwarg must be passed explicitly every time, it is never assumed.
- When genuinely stuck (same fix retried repeatedly, diminishing returns, a hard blocker — not just "this is slow"): generate a genuinely different strategy, try it in an isolated git worktree (`Agent` with `isolation: "worktree"`), verify it actually works before trusting it, then merge if better or discard cleanly if not.
- Chat output: no play-by-play narration of intermediate tool calls. Final message is a succinct result, a summary of what changed, and what's needed from the user if anything.
- **Merge PRs without asking** (user instruction, 2026-08-11: "merge, don't ask, just do it"). Open the PR, merge it, keep going — don't pause for approval on the merge step. Standing authorization for merges specifically, not a blanket waiver on genuinely destructive/irreversible actions.
- The user is **not a programmer**. Terminal instructions need to be literal, one command at a time, with what-you'll-see spelled out — and watch for interactive traps a developer would breeze past (vim opening on `git pull`, hidden password prompts, commands accidentally pasted onto one line). Set `git config --global core.editor "nano"` on their machine if vim comes up again.
- **Brave's plan is metered with a real $ spend cap, not the "no monthly cap" the earlier note claimed** — hit HTTP 402 (`current_spend:5.0, usage_limit:5.0, usage_limit_type:monthly`) on 2026-08-13, mid-session, partly from this session's own repeated diagnostic runs. `BRAVE_API_KEY_2` (a second account, added 2026-08-13) is now an automatic fallback in `brave_discover.py` — don't assume the primary key is live; check for the 402 pattern in logs first. `brave_consultas_por_run` lowered 600 → 100 (2026-08-16, user request) after key 2 alone had already reached half its own monthly cap. **✅ SUPERSEDED (2026-08-17): Tavily is now the sole SDB-scan provider, not a backup.** A real benchmark (`scripts/diagnostico_imobiliaria_crawl.py`, 30 real `imobiliaria` hosts) showed Tavily beating both Brave's old `site:` rotation and the no-API crawler on yield and speed. Both Brave keys were confirmed fully exhausted ($5/$5 on each) on 2026-08-16 *and* 2026-08-17, so Brave's SDB role was already dead in practice before being retired in code — Brave's only remaining job is `brave_discover.discover_novos` (the generic new-site hunt, its own `brave_novos` source/job), which still needs the key(s) to eventually recharge.
- **Apify has the same two-account pattern as Brave, added 2026-08-16 (user request)**: `APIFY_TOKEN_2` (a second free-tier account) is now the primary in `facebook.py::_via_apify`, `APIFY_TOKEN` an automatic fallback. Each account has its own independent monthly credit, so the local spend ledger is tracked per account (`apify_usd_1`/`apify_usd_2`, not one shared `apify_usd` counter) — a shared counter would keep blocking calls to a fresh account just because the other one's credit ran out.
- **Never let a candidate the pipeline found (a Brave/Tavily hit, an unblocker success) simply vanish on failure.** `brave_frios` (cold storage, added 2026-08-13) exists for exactly this: a URL that exhausts its retry budget moves there instead of being deleted, preserving both the URL and the search credit that found it for whenever a working transport exists. Apply this pattern before deleting anything a paid/metered call produced.

## Architecture / current state (as of 2026-08-13)

**What it does**: searches Brazilian portals + long-tail web/social for rural land for sale, filters/scores against `criteria.yaml`, publishes a sortable HTML page via GitHub Pages (`https://atismatiz.github.io/Terreno/`).

**Pipeline** (`terreno/run.py`): iterates `REGISTRY` sources (`terreno/sources/__init__.py`) enabled for the active profile (`ci` or `local`, in `criteria.yaml`), collects raw listings, normalizes/dedupes/filters/enriches/scores (`terreno/pipeline.py`), renders `site/index.html` (`terreno/render.py`), commits `data/terreno.sqlite3` + `site/` + `criteria.yaml` back to the branch, then a `deploy` job publishes to Pages.

**Sources**: `mercadolivre`, `pgfn`, `olx` (rewritten 2026-08-13 to use Playwright — see Known bugs, it was never actually blocked, its data just moved client-side), `chavesnamao` (via `htmlportal.py`), `caixa` (public CSV + `curl_cffi` for its bot wall), `brave`/`tavily` (long-tail discovery), `facebook`. Two are **disabled** as dedicated sources (direct fetch still fails): `vivareal` (`fontes.vivareal: false`, 2026-08-11 — misbehaves in an ordinary browser too) and `imovelweb`/`wimoveis` (`fontes.*: false`, 2026-08-12/13 — refused by ZenRows in both quick and `js_render` mode). **But as of 2026-08-13, wimoveis/imovelweb are no longer fully dark**: moved from `SKIP_HOSTS` to `COLD_HOSTS` in `brave_discover.py` — Brave/Tavily still find their listing URLs (a real Cloudflare JS challenge blocks every free transport tried, including a self-hosted headless browser, but not the *search* API), and results route straight to `brave_frios` (cold storage) rather than a live visit whose outcome is already known. **Only one profile exists now**: `perfis.ci = [brave, chavesnamao, caixa, pgfn, olx, facebook]` (`mercadolivre` removed 2026-08-14, see Known bugs; `perfis.local` and `scripts/run_local.sh` are gone, see Standing rules).

**Scoring** (`terreno/scoring.py`, 2026-08-11 rework): seven dimensions summing to 100 — Água 30, Benfeitorias 20, Acessibilidade 15, Silêncio 10, Aptidão agroflorestal e solo 10, Documentação 10, Topografia 5. Plus two modifiers outside the base, each exposed as its own row in `dimensoes`: **preço/ha** (bonus below `preco_por_ha.ideal`, penalty above `teto_alerta`) and **proximidade** to `localizacao.centro` (Monteiro Lobato). `motivo_descarte()` handles hard discards — dirt road >8 km, `contrato de gaveta`, non-rural, area <0.5 ha — kept separate from scoring so the caller decides. `estrelas()` surfaces cachoeira and similar without scoring them; `destaques()` builds the per-theme strings the Telegram card prints.

**Two output channels, deliberately different widths.** Everything scored reaches the site. Telegram gets a narrower list, gated in `run.py` by two rules that both *leave the listing on the site*: price per hectare above `teto_alerta` (`notificavel`), and already sold/removed (`terreno/disponibilidade.py`, checked in parallel over the shortlist only, where a network failure counts as available so an outage cannot delete a good listing).

**Photo reading** (`terreno/extract/imagem.py`): Haiku vision, gated to scores ≥ `saida.nota_minima_imagem` (70/100). Keywords are free and run on everything; images cost per listing, so the spend tracks the shortlist. Needs `ENABLE_LLM=1` + `ANTHROPIC_API_KEY`, otherwise it logs once and skips.

**Unblocker transport** (`terreno/http.py`): escalation is `requests` → `curl_cffi` → ZenRows. Off unless `TERRENO_UNBLOCKER=zenrows` and `ZENROWS_API_KEY` are both set (repository secret + variable, added by the user 2026-08-11). Hard per-process cap `TERRENO_UNBLOCKER_MAX_POR_RUN` (default 15 requests) because `brave_visit` walks the whole pending queue and could otherwise spend a month's free allowance in one run. Key is redacted from every log line.

**The user's local setup is working** (macOS, Python 3.13 at `/Library/Frameworks/Python.framework/Versions/3.13`): repo cloned at `~/Documents/Terreno`, `.env` filled in, `./scripts/run_local.sh` runs end-to-end, pushes results, and Telegram alerts arrive. Their `pip3` and `python3` point at **different Python installs** — always tell them `python3 -m pip install ...`, never bare `pip3`.

**Brave (Layer B)** is two decoupled phases, each its own module:
- `terreno/sources/brave_discover.py` — queries Brave (with `BRAVE_API_KEY_2` as an automatic fallback on a 402, added 2026-08-13), queues every new candidate URL into `brave_pendentes`. Never fetches a page. `brave_consultas_por_run` caps queries per run (600); `brave_consultas_por_mes` tracks the real, hit-in-practice monthly $ cap (see Standing rules — the "no monthly cap" note here was wrong). `SKIP_HOSTS` (covered by a dedicated source already) vs `COLD_HOSTS` (wimoveis/imovelweb, 2026-08-13 — findable but not visitable right now, see Architecture above) are handled differently: `SKIP_HOSTS` results are discarded, `COLD_HOSTS` results go straight to `brave_frios`. `sites_alvo` (hand-curated) and auto-discovered hosts now share one weekly-cooldown query rotation (`sites_descobertos_para_consultar`, via `sites_alvo_semear`) instead of `sites_alvo` being re-queried every single run regardless of whether anything changed. **2026-08-14: the generic templates now excludes already-known hosts.** Every result from a non-`site:` query is checked against `Store.hosts_conhecidos()` (every host already in `sites_descobertos`, promoted or not) plus the static `SKIP_HOSTS`/`COLD_HOSTS`; a hit on a known host is dropped (logged, not queued) instead of eating a visit slot re-covering ground the weekly `site:` rotation already owns. A genuinely new host gets queued for visiting *and* seeded into `sites_descobertos` immediately via `Store.sites_descobertos_avistar()` (occurrences start at 0 — actual promotion into the `site:` rotation still needs 2 real extractions, unchanged). This is the explicit split the user asked for: Brave's generic net is now for *finding new sites*, the `site:` rotation against `sites_descobertos` is the *daily-opportunities* channel from sites already known — and it's the one meant to keep working once the month's Brave quota (spent fast across keys 1&2) runs dry.
- `terreno/sources/brave_visit.py` — loads the pending queue and visits it in parallel (`ThreadPoolExecutor`, `brave_paralelismo: 50`), no per-run time or count cap. Per-page timeout `brave_timeout_pagina_s: 40`. Three outcomes per candidate: extracted a listing → done; fetched but nothing there → done (discarded, revisiting won't help); couldn't fetch at all → `falhas` counter +1, retried next run, moved to `brave_frios` **(cold storage, not deleted, since 2026-08-13)** after `brave_max_falhas: 2` consecutive failures. Also feeds `Store.registrar_extracao_brave()` on every successful extraction (auto-discovery, below).
- `terreno/sources/brave.py` is a thin orchestrator: `discover()` then `visit_all()`, same external `fetch()` signature the registry expects.
- The old shared 90s visit deadline is gone entirely — visiting was never actually API-limited (only discovery calls Brave), so the real backstop is the workflow job's own `timeout-minutes` (currently 90, in `.github/workflows/search.yml`), not an app-level budget.

**Auto-discovered sites** (added 2026-08-11): a host that isn't in `sites_alvo` but produces ≥2 real extracted listings (price/area actually read, not a category page) gets "promoted" in the new `sites_descobertos` table and joins the `site:` query rotation — on its own weekly clock (`ultima_consulta`), independent of how often the main pipeline runs. Logic: `Store.registrar_extracao_brave`/`sites_descobertos_para_consultar`/`sites_descobertos_marcar_consultado` in `terreno/store.py`, wired from `brave_visit.py` (recording) and `brave_discover.py` (querying + resetting the clock).

**Database** (`terreno/store.py`, `data/terreno.sqlite3`, committed to the repo): `listings`, `price_history`, `geocache`, `budget_ledger`, `runs`, `source_health`, `brave_pendentes` (url, dica, descoberto_em, falhas), `brave_frios` (url, dica, descoberto_em, motivo — cold storage, added 2026-08-13), `sites_descobertos` (host, ocorrencias, primeira_vez, ultima_vez, promovido_em, ultima_consulta). **Important**: `Store.__init__` runs `SCHEMA` via `CREATE TABLE IF NOT EXISTS` *and* an explicit `_migrate()` step — the schema-diff pattern needed any time a column is added to an existing table, since `IF NOT EXISTS` never alters a table that already exists and this DB is a committed file, not recreated per run. (A brand-new table doesn't need this — `CREATE TABLE IF NOT EXISTS` handles that fine on an old DB file.)

**Scoring's proximity bonus is 4-tier, not a single distance curve** (`terreno/scoring.py::ajuste_zona`, added 2026-08-13): tier 4 (highest) is an exact municipality-name match on `localizacao.centro` (Monteiro Lobato); tiers 2-3 are two named town lists (`localizacao.zona_melhor`/`zona_boa` in `criteria.yaml`, a best-effort translation of two hand-drawn map images — not yet confirmed town-by-town, corrections welcome); tier 1 (no named match, including an unknown municipality) falls through unchanged to the original continuous distance curve (`ajuste_centro`). `pipeline.score_all` passes `item.municipality` + the criteria lists into `scoring.avaliar`.

**Infra**: GitHub Actions (`.github/workflows/search.yml`) — cron daily at 09:00 UTC + manual `workflow_dispatch` (accepts `profile`, `overrides`, `salvar` inputs). GitHub Pages serves the static site. **Vercel** (`api/disparar.js`) exists only to hold the GitHub PAT server-side for a "run search now" button on the page — GitHub Pages can't hold secrets since it's static-only. User has Vercel "already configured" on their end but branch/env-var wiring for the button isn't confirmed done yet (see Pending).

**Search criteria** are still narrow test values: SP, Vale do Paraíba, 2–10 ha, R$100k–2M — the simplest lever to get more results is widening these.

## Known bugs & fixes (reference for anyone touching this again)

- **Apify's local cost ledger under-counted the real per-item price, and the real fix is Apify's own `maxTotalChargeUsd` run cap, not a better guess at `USD_POR_ITEM`** (found + fixed 2026-08-24, two corrections in one day). First pass wrongly concluded the account's real monthly credit was only ~US$ 1.65, from the local ledger's own estimate (`RESULTS_LIMIT × USD_POR_ITEM=0.005`, the actor README's flat per-result rate). The user then showed the real Apify billing dashboard (`Usage $5.00 / $5.00`, the whole credit burned by the Facebook Marketplace Scraper actor over ~5 days at the old `resultsLimit=30`) — the US$ 5/month cap in `criteria.yaml` was right all along; `0.005` was the wrong per-item rate, since the README's fee is only one line item and proxy/compute usage (separate dashboard line items) are billed on top and weren't counted. A second look at that account's own **Run history** (console.apify.com, not just the billing summary chart) gave the precise ratio instead of another guess: 8 real runs, 404 billed items total, US$ 5.00 total → **~US$ 0.0124/item**, 2.5x the README rate. Rather than keep re-deriving "how many items is safe" from a per-item estimate at all, `facebook.py::_apify_post` now passes Apify's own `maxTotalChargeUsd` (a run-level API query param, not an actor input field — see `docs.apify.com/api/v2/act-run-sync-get-dataset-items-post`) on every call, defaulting to US$ 0.15/run (env `APIFY_FB_MAX_CHARGE_USD`) — a hard ceiling Apify enforces itself regardless of which billing component actually drives the cost. `resultsLimit` is still sent too, now derived from the real ratio as a secondary soft cap (`round(0.15 / 0.0124)` ≈ 12, was 30). `apify_usd_por_mes` stays `5.00` (confirmed correct). Lesson: a metered API's own **run-level history/billing dashboard** is ground truth over its README's advertised per-unit price — and if the API offers a native hard spend cap per call, use that instead of computing one from an estimated rate.
- **Scoring's distance and price modifiers replaced with the owner's explicit stepped tiers** (2026-08-21, real bug the user flagged: a São Luiz do Paraitinga listing, ~61 km from Monteiro Lobato, scored 70/100 almost entirely on water/buildings/land-quality evidence, because `ajuste_centro`'s old continuous curve had a **flat 40-70 km "neutral" band worth exactly zero either way** — distance neither helped nor hurt a listing sitting 4x past the "close" threshold). `terreno/scoring.py` now uses discrete tier tables instead of continuous curves: `CENTRO_TIERS` (0-10 km `++`, 10-20 `+`, 20-30 `0`, 30-50 `-`, 50-70 `--`, beyond `---`) and `PRECO_HA_TIERS` (<80k `++`, <100k `+`, 100-149k `0`, 150-200k `-`, >200k `--`), each delta in {±0.15, ±0.08 or ±0.10, 0}. Added a new, independent absolute-price modifier (`ajuste_preco_absoluto`, `-0.05` above R$ 1 milhão, unrelated to R$/ha) and a new hard discard: no benfeitoria at all *and* R$/ha over 80.000 (`PRECO_HA_DESCARTE_SEM_BENFEITORIA`) drops the listing outright rather than merely penalizing it. Also raised `AREA_MIN_RURAL_HA` 0.5 → 2.0 ha (own explicit call) and retimed the acesso dimension's dirt-road tiers to <2 km `+`, 2-4 km neutral, >4 km `-` (was <2/≤5/≤8). `motivo_descarte()` and `avaliar()` both gained new parameters (`price_per_ha` on the former, `price` on the latter) — `pipeline.score_all`'s two call sites updated to pass them. Verified against the real São Luiz do Paraitinga text: nota dropped from 71.7 to 62.0 once the -10% "50-70 km" tier actually applied, and the two new discard rules fire/don't-fire correctly on synthetic cases.
- **Area parsing missed the common Brazilian abbreviation "mts"** (found 2026-08-21 against a real hsimoveisrurais.com.br listing whose own page clearly stated "ÁREA TOTAL: 34.000 mts" but whose Telegram card showed "área não informada"): `terreno/units.py`'s `_UNIT_HA` table recognized `m2`/`m²`/`metro(s)`/`m` but not `mts`. Added `"mts": 1e-4` alongside the other m² aliases; verified `area_to_ha(...)` now returns `3.4` ha for that exact text.
- **Facebook listings 100+ km outside the search region still reached Telegram** (found 2026-08-17, two real results the user flagged: Joanópolis/SP and "Ajapi" — actually Rio Claro/SP, ~150km+ from Vale do Paraíba): both sellers' own descriptions stated the real city in exactly the shape `rules.py`'s location regex already parses ("Joanópolis-SP", "RIO CLARO/SP"), but `facebook.py::_from_apify` only ever trusted Facebook's own (often-empty) structured `location` field and never fell back to the description text — leaving `municipality=""`, which silently disables the region whitelist *and* radius filters in `pipeline.apply_filters` (both require a non-empty `municipality` to even run). Worse, when Facebook's own state field was also empty, the code defaulted `uf` to whatever state the search itself targeted (an unproven assumption dressed as a fact). Fixed: new `rules.municipio_do_texto()` (shared, lazy-imported into `facebook.py` to dodge a circular import) parses title+description text as a fallback whenever the structured fields come up empty; the search-target-state default is now a true last resort, tried only after the text fallback. Once `municipality` is set, the *existing* whitelist filter correctly excludes both real listings — no changes needed to `pipeline.py` itself.
- **Telegram silently dropped a genuine new listing with no visible reason** (found 2026-08-17: a real run logged "10 matches, 4 new" but only 3 cards reached the chat). (2) `run.py` excluded any new listing whose R$/ha was above the notification ceiling (`notificavel`) from Telegram specifically, while still showing it on the site — per the user's explicit call, every new listing now gets a Telegram card, always; `notificavel` is still computed and shown, just no longer a reason to withhold the alert. `run.py`'s call to `notify.telegram` also stopped passing a `top_n` cap below the real count (was `criteria.output("top_n_no_alerta", 8)`, now `len(para_avisar)`) — the now-dead `saida.top_n_no_alerta` config key was removed.
- **The site's "Ver todos"/`TERRENO_PAGE_URL` fallback pointed at GitHub Pages, but the real page users open is a separate Vercel deployment** (`terreno-omega.vercel.app`, which also hosts `/api/disparar` — GitHub Pages can't serve that). Fallback default in `run.py` switched to the Vercel URL, 2026-08-17.
- **Health-alert label said "brave" for a source that no longer uses Brave at all** — `REGISTRY`'s `"brave"` key (the daily SDB scan, now 100% Tavily since the 2026-08-17 Tavily-covers-everything change) kept accumulating its `source_health` streak under the old name, so "Fontes sem resultado • brave: sem resultado há 3 execuções seguidas" kept firing in Telegram even though Brave itself wasn't being asked anything. Renamed the REGISTRY key to `sdb_scan` (in `terreno/sources/__init__.py` and `criteria.yaml`'s `fontes`/`perfis.ci`) — a fresh, accurately-named health streak starts from zero. Individual listings still carry `source="brave"` (`brave_visit.py`'s `NAME`) for per-card attribution on the site; that's a separate, unrelated concept from the REGISTRY key and was deliberately left alone.
- **No age check at all — an 8-year-old LinkedIn "pulse" post read as a live sítio listing** (found 2026-08-17, real result the user flagged): a well-written, grammatically genuine listing with a real price and area, dated 2018, discovered via Brave.
